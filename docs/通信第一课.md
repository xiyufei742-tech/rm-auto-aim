# 通信第一课：让自瞄程序和比赛下位机说同一种话

**今天的目标（约 1 小时）：** 在这个比赛项目里，看懂电脑要发给云台什么、车会回传什么。今天运行的是协议演示，数据在电脑内存里生成；不需要相机、车或比赛视频。

## 先认识两个角色

- **上位机**：运行本项目的电脑。以后它根据相机图像算出目标云台角度。
- **下位机**：车上的控制板。它接收目标角度，控制云台，并把当前云台角度等状态发回来。
- **USB CDC 虚拟串口**：两者之间的数据通道。在 Linux 上常显示为 `/dev/ttyACM0` 之类的设备名。你现在不用连接它。

“通信协议”就是双方约定：每个数字用几个字节、按什么顺序摆、单位是什么。**字节**可以理解为传输时的一格数据；一组按规则排好的字节叫一**帧**。

## 亲手运行项目里的协议

在终端输入：

```bash
cd /path/to/rm自瞄
./运行.sh 通信
```

第一次会编译几秒到几十秒。最后请找这三处输出：

1. `完整发送帧：10 00 ...`：电脑准备发送 **18 字节**。开头的 `10 00` 按“小端”读是十六进制 `0x0010`，即十进制 **16**；它表示后面数据体有 16 字节，再加长度自身的 2 字节，总共 18 字节。
2. `第一次 read 只收到 7 字节：解析出 0 帧，缓存 7 字节`：一次读取可能只拿到半帧，先存起来。
3. `第二次 read 收到余下 23 字节：解析出 1 帧`：凑足 **30 字节**后，才得到车的完整回传。这是按正式协议构造的示例数据，不是实车测量值。

这里的 `read` 就是程序从串口取字节的动作。“小端”只表示多字节数字的低位字节先放；今天能认出 `10 00 = 16` 就够了。

## 18 字节发送帧到底是什么

| 字节位置（从 0 数） | 内容 | 本次示例 |
| --- | --- | --- |
| 0–1 | 后续数据长度 | 16 字节 |
| 2–3 | 记录 ID 1 | 后面是云台目标 |
| 4–7 | yaw：左右角度，float32 | 1.25 度 |
| 8–11 | pitch：上下角度，float32 | −0.5 度 |
| 12–13 | 记录 ID 2 | 后面是开火请求 |
| 14–17 | fire_flag：int32 | 0，不请求开火 |

`float32` 是占 4 字节的小数；`int32` 是占 4 字节的整数。你暂时不用手算它们的二进制。项目中的 `encodeCommand()` 已经负责按协议摆好这些字节。**角度单位是度**，这个点以后接瞄准算法时要特别留意，因为算法内部可能用弧度。

回传帧总共 30 字节，包含当前 yaw、pitch、roll（度），`mode`、`robot_id` 和 `bullet_speed`（米/秒）。其中 `mode` 在参考协议里写为保留字段；本车现场拨档时实际观察到 `0→1→0`，因此必须区分协议文档和本车实测。协议中名叫 `color` 的字段当前表示机器人 ID，不要拿它直接当敌方颜色。详细字段见[正式通信规则](规则/self_aim_protocol.md)。
