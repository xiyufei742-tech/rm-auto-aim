※ 源码与术语约定

本文把 Armor 叫“装甲板观测”，把 Target 叫“连续目标状态”。源码里角度常用弧度 rad，正式协议用度 deg；三维长度用米，像素坐标用 px。看到数字先问单位。代码链接均指向本文件夹内的实际文件。原算法归属同济 SuperPower sp_vision_25；比赛协议与现场工具是此工程新增内容。

第一章　总链路与数据类型

本章主线：画面 → 四角与类别 → 三维观测 → 连续运动状态 → 未来瞄准角 → 协议字节。读代码先看“一个变量是什么”，再看公式。
cv::Mat 图像→YOLO：Armor 列表→Tracker + Solver：Target→Aimer：Command→encodeCommand：18 字节→模拟云台回传

1.1 一帧如何变成命令

回放入口 system_replay.cpp 是最直观的阅读顺序。每次循环读取一帧及录制姿态，调用 solver.set_R_gimbal2world(q)，再依次调用 yolo.detect、tracker.track、aimer.aim。最后将角度转为度，encodeCommand(..., 0) 编码并通过虚拟串口发送。这里 0 是明确的禁射请求；aimer.aim(..., false) 中的 false 是 to_now，表示回放时使用另一种预测时间处理方式。

◈ 四个数据盒子
类型里边有什么怎么理解
cv::Mat某一时刻的 BGR 图像只有像素，没有真实距离。
Armor颜色、类别、置信度、四角、PnP 后的位置与姿态一帧中的观测；四角顺序必须固定。
Target目标旋转中心、速度、角度、半径、高度差和滤波协方差跨帧维护的状态，可预测未来。
io::Commandcontrol、shoot、yaw、pitch算法内部结果，尚未是比赛报文。
源码：armor.hpp、target.hpp、command.hpp
⚠ 不要把输出计数当成绩

回放中“120 帧里 96 帧检出”仅表示某段演示录像里检测器返回了候选；没有人工真值就不能算准确率，更不能推算靶板命中率。录播图像不随模拟云台转动，所以它也不是视觉反馈闭环。

第二章　视觉检测与四角

本章主线：配置选择模型 → 缩放到网络输入 → OpenVINO 推理 → 解码置信度、类别和四角 → 非极大值抑制 → 几何筛选。

2.1 当前配置实际选择什么

demo.yaml 和 live_yolo.yaml 都设置 yolo_name: yolov5。YOLO::YOLO 根据该字符串创建 YOLOV5，所以教材主讲 yolov5.cpp。仓库里的 YOLOv8、YOLO11 是可选实现，此配置没有调用。现场配置还将 use_traditional 设为 false；演示配置为 true，会在网络四角后尝试传统方法二次修正。

2.2 预处理为什么必须能反算

代码把原图或 ROI 按同一比例缩进 640×640 黑底输入。设原图宽 W、高 H，则缩放系数是 s = min(640/H, 640/W)。网络输出的坐标位于缩放图上，代码用 x_original = x_net/s、y_original = y_net/s 还原。如果启用 ROI，还须把裁剪起点加回去。四角若落错坐标系，PnP 再精确也会解错。

✦ 例题｜1440×1080 画面缩放

假设不开 ROI：s=min(640/1080,640/1440)=4/9≈0.4444，缩放后的画面为 640×480，其余像素填黑。网络给出某角点 (320,240)，反算原图约 (720,540)，恰为图像中心。注意这是几何换算示例，并非实机标定结果。

2.3 神经网络、置信度与 NMS 的入门概念

传统图像算法先由人写规则，如“亮度超过阈值且细长的区域可能是灯条”；神经网络则在训练阶段用大量标注样本调整参数，使输入图像映射到候选位置、类别和四角。训练是改模型参数，推理是用固定参数计算一张新图的结果；当前工程运行的是 OpenVINO 推理，并没有在比赛程序里训练模型。

◈ 置信度与非极大值抑制

网络对同一块板可能给出好几个相近候选。置信度是模型内部的评分，不等于“有 90% 概率绝对正确”。NMS 把候选按评分排序，对重叠过高的低分框进行抑制，保留代表性结果。它主要去重复，不能修复错误分类和错误四角。阈值太高会漏检，太低会增加误检；应在比赛录像上比较不同场景的结果。

关键点检测比只输出矩形框多给了四个角。矩形框足以画出“哪里有目标”，PnP 则需要每个二维角与哪个三维物理点一一对应。

2.4 后处理究竟做了什么

YOLOv5 实现从每行输出读取四角、类别与颜色分数，并对位置置信度调用 sigmoid；未到阈值的候选先丢弃。剩余候选做 cv::dnn::NMSBoxes，即把高度重叠的重复框压到少数几个。然后构造 Armor、检查装甲板名称与类别、可选用传统方法修角点。代码里四点的入列次序是左上、右上、右下、左下，对应 Solver 里的物理点顺序。

四角是模型/构造器和 PnP 共同遵守的对应关系，目标旋转时仍要追踪同一物理角。
⚠ 检到四角不代表测到物理尺寸

比赛靶板标称 140×125 mm，但同济 Solver 用的是灯条点间距 135/230 mm 与灯条长度 56 mm。若网络四角实际落在灯条上的位置与这组物理点不对应，直接把“140×125”替换成点距同样可能错。先在现场确定四点的物理定义，再改 PnP 模型。

第三章　PnP 与坐标变换

本章主线：二维角点加已知三维尺寸，求装甲板相对于相机的位姿；再把它转换到云台与世界坐标。

3.1 内参、畸变、外参分别解决什么

◈ 三类参数
  • 内参 K：fx, fy, cx, cy 定义相机坐标投到像素的位置。近似无畸变时 u=fx·X/Z+cx、v=fy·Y/Z+cy。
  • 畸变 D：描述镜头让理想直线或位置偏移的程度；OpenCV PnP 同时接受 K 和 D。
  • 外参：R_camera2gimbal、t_camera2gimbal 描述相机相对于云台怎样安装；它们不是镜头内参。

3.2 PnP 求解链

Solver::solve 按装甲板大小选择四个物理角点，调用 cv::solvePnP(..., cv::SOLVEPNP_IPPE) 得到旋转向量 rvec 和平移 tvec。tvec 表示装甲板坐标原点在相机坐标系的位置（米）。然后用以下两步转换：

∑ 坐标链
p_g = R_c→g · p_c + t_c→g
p_w = R_g→w · p_g

c 是 camera，相机系；g 是 gimbal，云台系；w 是 world，世界系。矩阵相乘的顺序不能倒。R_g→w 来自每帧云台/IMU 姿态，回放从演示姿态文件读取；比赛现场接入时也需要有可信的对应姿态。

3.3 为什么要重投影

已知三维位置和旋转，就可以反过来将物理四角投回图像。Solver::reproject_armor 用 cv::projectPoints 完成这一步；投影点与网络四角之间的像素差称为重投影误差。误差突然变大，常见原因是四角顺序错、识别漂移、物理角点模型错或相机参数错。optimize_yaw 还在候选角范围里搜索较小的重投影代价；它不能修复错误标定。

3.4 PnP 为什么能从平面四角求出距离

想象一个已知宽高的纸片：近处看得大，远处看得小；斜着看时两边形状也会变化。PnP 把这种透视关系写成“假定某个三维旋转与平移 → 投到图像 → 与实测四角比较”的求解问题。它的未知量主要是目标相对相机的旋转和平移；已知量是四个物理点的坐标、对应的像素点、相机 K 与 D。只有图像点、没有物理尺寸时，尺度无法凭空确定。

∑ PnP 的直观目标
寻找 R、t，使 Σᵢ‖project(K,D,R·Pᵢ+t) − uᵢ‖² 尽量小

Pᵢ 是第 i 个物理角点，uᵢ 是图像角点；project 包含透视投影和镜头畸变。实际 SOLVEPNP_IPPE 针对平面点有专门处理；上式用于理解“为什么点、尺寸和标定必须正确”，不是对 OpenCV 内部实现的逐行复刻。

✦ 例题｜粗略距离敏感性

仅为直觉，正对目标时可用 Z≈f·W/w：若 f=1800 px、物理宽 W=0.135 m、图上宽 w=48.6 px，估计距离约 5 m。若误把真实点距 0.140 m 当 0.135 m，距离会按相同比例偏约 3.7%。正式结果仍以带畸变的 PnP 与现场标定为准。

⚠ 当前现场配置的参数不可直接用于正式距离

live_yolo.yaml 里的 K、D、相机到云台变换仍来自开源演示设备。现场已验证的是像素方向和小角度 yaw 响应，没有完成本车真实镜头的内外参标定。因此“程序能编译并跑出 PnP 数字”不能算距离正确。

第四章　跟踪状态机

本章主线：同一帧可以有多个候选，连续帧也可能漏检。跟踪器负责选择对象、维持身份并决定何时作废目标。

4.1 四个关键状态

Tracker::state_machine 的主要路径是 lost → detecting → tracking → temp_lost → lost。第一次见到目标后，先进入 detecting，连续检出达到 min_detect_count 才成为 tracking。偶尔漏检可进入 temp_lost 保留一段时间，超过 max_temp_lost_count 则回到 lost。多相机分支还会用 switching，当前单路回放调用的是较简单的重载。

∑ 时间断流检查

源码计算相邻时间戳 dt。若已有目标而 dt>0.1 s，直接将状态改成 lost。这条规则防止相机停顿后继续使用旧状态预测。假设 100 fps，正常两帧间隔约 0.01 s；0.12 s 断流已经跨过十余帧。

4.2 选谁、何时更新

跟踪器先按 enemy_color 过滤，再考虑图像中心距离和装甲板优先级。拿到候选后，set_target 用 PnP 初始化目标；后续 update_target 先预测，再按名称与大小匹配观测，并逐一 solver.solve、target.update。它会检查目标半径是否发散和 EKF 创新异常；不可信时清空目标。

⚠ 两处需要现场核对
  1. 排序代码把画面中心写死为 (720,540)，对应 1440×1080。若换分辨率或 ROI 坐标处理变化，优先级可能偏。
  2. 某一帧没有新检测，也可能暂时返回预测 Target；所以“有跟踪目标的帧数”可以大于“检出装甲板的帧数”。这并不自动意味着预测正确。

第五章　目标运动估计：11 维 EKF

本章主线：把一帧装甲板位置看成测量值，把车体旋转中心及其运动看成隐藏状态，用预测和观测更新不断修正。

5.0 先懂普通卡尔曼滤波

假设你要知道云台的真实 yaw。编码器读数会抖，上一时刻的角度加上运动模型也会有误差。卡尔曼滤波把二者当成“带不确定性的两条信息”：模型预测告诉我们大概会到哪里，新传感器读数告诉我们实际可能在哪里。谁更可信，就给谁更大权重。它不是简单把最近几帧取平均；它会同时维护估计值和不确定性。

◈ 从 1 维开始认符号
符号含义直观理解
x隐藏的真实状态的估计例如估计 yaw 为 10°；我们不知道真值，只能估计。
z新测量例如本次读到 12°，测量本身会抖。
P状态估计误差协方差1 维时可当成“不确定性大小”；多维时还表示不同变量误差是否一起变化。
Q过程噪声协方差运动模型没描述到的加速、碰撞或转速波动。
R测量噪声协方差角点抖动、PnP 误差等让新观测不可靠的程度。
K卡尔曼增益本次更新该多大程度信任新测量。

P/Q/R 是方差或协方差量，量纲是相应状态或观测单位的平方；它们不是 0～1 之间的“置信度百分比”。

∑ 最简单的 1 维更新
K = P⁻/(P⁻ + R)
x⁺ = x⁻ + K(z − x⁻)
P⁺ = (1−K)P⁻

上标 − 表示看到本次测量之前的预测；+ 表示融合后的结果。若 R 很大，测量不可信，K 小，结果更靠近预测。若 P⁻ 很大，预测不确定，K 大，结果更靠近新测量。这个式子假设直接测到状态；一般情况还需要观测矩阵 H。

✦ 手算一遍，才会真正理解“融合”

预测角度 x⁻=10°、预测方差 P⁻=4 deg²；新测量 z=12°、测量方差 R=1 deg²。那么 K=4/(4+1)=0.8，更新后 x⁺=10+0.8×(12−10)=11.6°，P⁺=(1−0.8)×4=0.8 deg²。结果靠近测量，因为我们认为测量比预测更稳。若把 R 改成 16 deg²，K=0.2，结果只到 10.4°。

⚠ 两种常见误解

一是“卡尔曼滤波会自动知道目标怎么运动”：运动模型仍由人设计，模型错会系统性预测错。二是“Q/R 调到画面看着平滑就好”：R 过大可能滞后，Q 过小可能对加速反应慢；要用下一帧预测误差、实际延迟和失败日志验证。

5.1 为什么需要状态，而不直接追每帧中心

同一辆车旋转时，面向相机的装甲板会不断切换；单块装甲板的像素中心会突然跳到另一块。Target 建模旋转中心和每块装甲板半径，推算未来哪块板会出现。这样 Aimer 可以考虑飞行时间，而不只追当前看到的点。这套整车模型是同济为 RoboMaster 车辆设计的。本赛是 5 米原地旋转靶，靶板真实几何和运动模式若不同，不能默认整车模型参数适用。

◈ 状态向量的 11 个分量
x = [cₓ, vₓ, cᵧ, vᵧ, c_z, v_z, a, ω, r, ℓ, h]ᵀ

c 是旋转中心位置，v 是对应速度；a 是装甲板相位 yaw，ω 是角速度；r 是一组装甲板半径，ℓ 是交替装甲板的半径差，h 是高度差。源码用 x[0]、x[2]、x[4] 表示中心坐标，x[7] 表示角速度。长度单位 m，角度 rad，速度 m/s、rad/s。

5.2 预测与更新各做一件事

∑ 预测步
cₓ(t+Δt)=cₓ(t)+vₓΔt
a(t+Δt)=wrap(a(t)+ωΔt)

y、z 同理。源码用状态转移矩阵 F 和过程噪声 Q；后者允许目标加速、旋转速度变化。wrap 把角度拉回周期范围，避免从 +179° 到 −179° 被误算成转了 358°。

∑ 观测更新步

观测向量是 z=[观测方位 yaw, 观测仰角 pitch, 距离, 装甲板朝向 yaw]。由当前状态预测某块装甲板位置，再变成预计的 ẑ=h(x)；测量与预测之差是创新。EKF 通过雅可比矩阵 H 和测量噪声 R 决定修正幅度。观测不稳时应更少信它；源码的 R 会随角度和距离改变。

5.3 装甲板几何模型

对于编号 i，代码算 angle=a+i·2π/N，并用 armor_x=cₓ−rᵢ cos(angle)、armor_y=cᵧ−rᵢ sin(angle)、armor_z=c_z+hᵢ 还原板的位置。四板车中第 1、3 块可以使用不同的半径与高度；前哨站和其他类别的板数及初始化半径也不同。

✦ 例题｜只看角度预测

若 ω=2 rad/s，从图像采集到弹丸到达目标还需 0.10 s，则相位变化约 0.20 rad≈11.5°。这个数解释了“原地旋转也需要考虑时间”；它不是本车实测延迟，也没有包含板的几何、云台响应和弹道。

⚠ EKF 输出不是测量真值

滤波器能使轨迹平滑，但错误尺寸、错误姿态或错误角点会让它稳定地估出错误状态。真正要核对的是：预测位置重投影是否贴住下一帧目标、角速度是否与靶板运动方向相符，以及丢帧后是否及时失效。

5.4 从普通 KF 到 EKF：非线性在哪里

普通卡尔曼滤波最方便处理线性关系：xₖ≈F xₖ₋₁、z≈H x。本项目从旋转中心到装甲板位置用到 sin/cos，再把三维坐标转成方位角、仰角和距离用到 atan2 与开方，观测关系是非线性的 z=h(x)。扩展卡尔曼滤波（EKF）在当前估计附近求导，用雅可比矩阵近似这个局部关系。雅可比就是“每个观测对每个状态变量有多敏感”的偏导数表。

∑ EKF 的预测—校正骨架
预测：x⁻=f(x⁺旧)，P⁻=F P⁺旧 Fᵀ+Q
创新：y=z−h(x⁻)，S=H P⁻ Hᵀ+R
增益：K=P⁻HᵀS⁻¹
更新：x⁺=x⁻+K y

F 是状态模型在当前点附近的线性化矩阵，H 是观测函数 h 的雅可比。源码里 Target::predict 给出 F/Q/f；Target::h_jacobian 给出 H；Target::update_ypda 定义 h/R/z；真正的矩阵融合在 extended_kalman_filter.cpp。该实现还用 Joseph 形式更新 P，以降低数值舍入造成的协方差问题。

✦ 为什么雅可比与装甲板方向有关

简化为 x_armor=cₓ−r cos(a)。那么它对相位角的导数为 ∂x_armor/∂a=r sin(a)：在某些朝向，角度小变化带来明显的水平位置变化；在另一些朝向，变化很小。因此同样 1° 的相位不确定性，在画面不同位置会投出不同的像素不确定性。源码 h_jacobian 就在做这类局部敏感度计算。

5.5 角度周期、创新和异常值

创新 y=z−h(x⁻) 是“测量和预测差了多少”。角度不能直接普通相减：预测 +179°、测量 −179°，真实差是 2° 而不是 −358°。源码在状态相位相加和观测差分时调用 limit_rad。若创新持续异常，可能是板切换匹配错、PnP 突跳、模型尺寸不对或时间戳错误；跟踪器还有半径发散检查与最近异常计数。

⚠ 源码里的“NIS/NEES”不要当教科书阈值使用

标准 NIS 通常用更新前创新 y 和 S 计算 yᵀS⁻¹y，再按观测维度选卡方阈值。当前 extended_kalman_filter.cpp 在更新状态与协方差后重新算残差和 S，且把 4 维观测的“95% 阈值”写成 0.711；这不能直接解释成标准 95% 卡方门限。代码中的 NEES 也使用新旧状态之差，而标准 NEES 要比较估计与真实状态。教材只把这些计数当现有实现的诊断信号，不能据此宣称滤波具有统计上的 95% 可靠性。

5.6 怎样用日志检验滤波，而不只看曲线平滑

  1. 固定静止靶：记录每帧四角、PnP 方位和滤波方位；看噪声大小与系统偏差。
  2. 让靶匀速转动：把第 k 帧预测到第 k+1 帧的角度，与下一帧真实检测比较；记录平均误差、峰值、漏检后恢复时间。
  3. 人为加入少量漏检或时间间隔：检查 temp_lost 与 lost 是否按预期切换，避免旧目标被无限预测。
  4. 每次只改一组 Q/R 参数，保留同一视频和配置版本进行比较；不要从单张截图判断好坏。

第六章　瞄准与弹道

本章主线：目标会动，弹丸要飞一段时间。瞄准器选择可射击装甲板，先估未来位置，再算应给云台的角度。

6.1 choose_aim_point 选哪块板

Aimer 从 Target::armor_xyza_list() 得到每块装甲板的预测位置和朝向。若目标尚未发生过装甲板切换，只知道当前板，便选它。发生切换后，低旋转速度分支在可射击角范围内选择，并有锁定机制避免相近的两块板来回跳；高速分支考虑旋转方向与进入、离开角。comming_angle 是源码和配置里的拼写，查找时按实际字段名。

6.2 时间提前量与两次预测

Aimer::aim 先按目标角速度选高/低速度延迟参数，并预测到处理、通信等延迟后的 future。随后根据初始瞄准点和弹速计算弹丸飞行时间，再把目标预测到 future + fly_time。飞行时间依赖目标距离，而未来目标距离也依赖飞行时间，所以代码最多迭代十次，直到相邻飞行时间差小于 0.001 s；若不可解则不给控制目标。

∑ 不计空气阻力的弹道方程
h = d·tanθ − g·d²/(2v²cos²θ)
t_fly = d/(v·cosθ)

d 为水平距离（m），h 为目标相对高度（m），v 为弹速（m/s），θ 为抬头角（rad）。Trajectory 把 tanθ 化为一元二次方程，若判别式为负则标记 unsolvable，否则选飞行时间更短的一支。

✦ 例题｜飞行时间的第一眼估计

假设水平距离 5 m、弹速 22 m/s、抬头角较小，粗略 t≈5/22≈0.227 s。若靶板角速度 2 rad/s，这段时间相位可转约 0.45 rad≈26°。这只是量级估计；正式提前量还需实际弹速、轨迹、延迟和运动数据。

6.3 输出的角度及风险

最终 yaw 为 atan2(y,x)+yaw_offset；pitch 取弹道抬头角与偏置的负值，因为源码世界坐标系把“向上”定义为负 pitch。若目标为空、射击窗口不合适或弹道不可解，返回 control=false。源码还在弹速低于 14 m/s 时以 23 m/s 代替，这属于同济原工程的回退假设；比赛现场必须用实测回传和弹道验证，不能把默认值当真。

⚠ 角度偏置不是标定的替代品

yaw_offset/pitch_offset 只能修正小的系统偏差；若 K、D、外参、角点物理模型或云台姿态本身错了，仅靠调偏置会在另一位置再次失准。当前回放用了同济演示参数，因此输出角度只说明算法在演示素材上运行。

第七章　比赛协议衔接

本章主线：同济算法的 Command 不是本赛下位机能直接识别的字节流。比赛适配层负责单位换算、固定帧编码与回传解析。

7.1 发送与接收布局

回放入口把 command.yaw/pitch 从弧度乘 180/π 转为度；没有有效控制时保留回传角度，再调用 encodeCommand。正式协议无魔数和 CRC，长度字段与 ID 记录必须严格匹配。

方向总长度内容
上位机 → 下位机18 字节2 字节 body_len=16；ID 1 + yaw/pitch 两个 float32；ID 2 + fire_flag int32
下位机 → 上位机30 字节2 字节 body_len=28；ID 1 + yaw/pitch/roll/mode/color；ID 2 + bullet_speed

所有字段是小端。USB CDC 是字节流，单次 read 可能只有半帧，也可能有多帧。FeedbackParser::feed 保留不完整数据；满 30 字节后检查长度和 ID，再提取姿态与弹速。协议没有可靠的任意字节重同步依据，非法帧时清空当前缓存。

★ 为什么“算法说可以开火”仍不等于能发射

同济 io::Command::shoot 与本赛 fire_flag 是两个层次。当前整链路回放明确发送 fire_flag=0；无弹像素跟随也固定为 0。即使将来视觉侧请求非零，下位机仍需同时满足人工许可和火控条件。实机发射与命中必须按靶板传感器核实。

⚠ 禁止把旧协议入口当比赛程序

同济 src/standard.cpp 依赖自己的 CBoard 通信；standard_mpc.cpp 使用原工程云台接口。它们保留作算法参考，并未因为编译成功就变成正式比赛串口程序。当前回放及现场工具使用新增 contest/protocol.*。

正式协议依据：SRM 校内赛自瞄通信协议

第八章　已验证的实机分支：像素闭环

本章主线：现场还没有可靠 PnP 标定时，先用装甲板中心的像素误差，验证相机、云台方向、串口和图像反馈能连起来。这条分支只控制 yaw。

8.1 它复用了同济算法的哪一块

srm_live_pixel_follow_safe 使用 auto_aim::YOLO 检出候选装甲板，再选目标中心 target_x；它没有调用 Solver、Tracker、Target、Aimer。后续像素修正来自本项目 pixel_follow_policy.hpp，并通过正式协议发送给下位机。把它称作“完整同济自瞄已上车”会误导读者。

∑ 像素误差到 yaw 小步目标
eₓ = x_target − (W−1)/2
Δyaw ≈ −eₓ / k ，k = Δx/Δyaw

10 月 11 日手动扫描测得 k≈+32.1 px/°。目标在图像右侧时 eₓ>0，故应减小 yaw。程序把单次更新限制在 ±0.15°，总行程限制在起点 ±2°，并设置 3 px 死区。这是当前相机、安装和位置的现场经验斜率，不是相机内参，也不能用于测距。

8.2 已看到的结果与尚欠的证据

现场一次 −0.3° 小步命令使云台约移动 −0.27°，装甲板中心向画面中心移动约 7–8 px；连续无弹跟随中 yaw 约从 −52.67° 到 −54.65°，目标从 x≈834 到 x≈770，随后触发 ±2° 限位。该次起点偏差超过可修正范围，因此尚未验证目标完全居中。旋转靶预测、pitch、PnP、弹道与开火仍待验证。

※ 如何与完整算法衔接

下一阶段先做本车标定、四物理角点确认、无弹静态 PnP 校验与 pitch 方向校验；然后将 Solver/Tracker/Aimer 与正式协议接到同一现场主循环，逐步比较“预测目标角”和“实际回传角”。可保留像素控制作独立的方向检查工具，避免两个控制入口同时占用相机或串口。

第九章　仓库里有，但当前比赛链路未接入的算法

本章主线：“代码存在”“开源原队伍用过”“本比赛已使用”是三个不同结论。本章讲清 Shooter 和 MPC Planner 的位置。

9.1 Shooter：根据云台误差判断射击时机

Shooter::shoot 在 auto_fire、有效目标和控制命令都满足时，比较相邻命令跳变量与云台实际 yaw 跟随误差，并按距离选容差。它的结果只是同济算法内部的开火判断；当前 system_replay.cpp 没有调用 Shooter，正式比赛的 fire_flag 仍固定为 0。不能把配置里某处的 auto_fire: true 当作实机已经会发射。

9.2 Planner：按云台加速度规划可跟随轨迹

Planner 使用 TinyMPC，对未来一段目标 yaw/pitch 轨迹求满足最大加速度约束的规划轨迹；它还能比较预期射击轨迹与规划轨迹在发射延迟后的偏差，生成开火判断。同济 standard_mpc.cpp 是它的原工程入口。当前比赛回放调用的是 Aimer，不是 Planner；现场像素跟随也不用它。

∑ 规划思想的最小模型
状态 s=[角度, 角速度]ᵀ
下一步：角度'=角度+角速度·Δt；角速度'=角速度+角加速度·Δt
|角加速度| ≤ 云台最大可用加速度

目标轨迹突然换板时，直接让云台追跳变指令会滞后或超调；规划器试图给出电机能跟上的平滑轨迹。但本赛正式报文只有 yaw/pitch 目标角和开火字段，没有原工程的角速度、角加速度前馈字段。即使以后用 Planner，也必须重新设计与下位机能力匹配的接口与验证。

9.3 MPC 和普通 PID 在这里分别解决什么

PID 常用当前目标与实际角度的误差算控制量；它主要回答“这一刻怎么纠偏”。MPC（模型预测控制或这里使用的有限时域优化）先利用运动模型模拟未来多个时刻，在限制条件内选择一串控制输入；它回答“接下来一段轨迹怎样更容易跟随”。此仓库的 Planner 以角度和角速度为状态、角加速度为优化输入，并给出最大加速度约束。它不是本比赛当前现场 yaw 像素跟随的控制器，也不能替代下位机实际电机控制。

⚠ 不把高级模块当优先完成项

本赛的确定任务是 5 米旋转靶，且计分按有效命中数除以 50。当前主要证据缺口是现场标定、四角模型、完整跟随和实弹落点。MPC 增加复杂度，只有在基础链路经现场数据证明是瓶颈时才值得接入。
