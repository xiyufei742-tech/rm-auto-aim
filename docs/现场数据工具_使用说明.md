# 10 月 13 日现场数据工具：操作与算法说明

## 1. 现在先看哪里

本说明解释现场数据工具怎么用、输出是什么、结果能说明什么。当前总体进度和下一步见[阶段成果与待办](阶段成果与待办.md)。

本次工具服务于三个问题：

1. 装甲板为什么会检出或丢失？用同一会话的原画面与逐帧数据一起查。
2. 画面变化和 yaw 变化是什么关系？用固定靶、手动慢扫得到局部拟合结果。
3. 怎样把像素位置变成可信的空间位置？先标定内参，再做离线 PnP 和实测距离对照。

已有无弹云台程序的控制逻辑、限位和开火标志没有在本轮修改。新采集、分析和标定工具不会发送云台指令。实机跟随仍用 10 月 11 日的受限程序，具体操作见现场总计划。


**正确版本的帮助信息：**探针应含 `--session`、`--phase`；相机程序应含 `--record-path`、`--duration-sec`。出现 `Built target ...` 只证明编译成功，不代表已经打开相机。

## 5. 同时记录原画面、识别结果和串口回传

### 5.1 固定靶、手动档，先录静止数据

保证当前没有别的相机程序在运行：

```bash
./build/srm_live_pixel_probe --config configs/live_yolo_1011.yaml --port /dev/ttyACM0 --frames 900 --display --phase static --session output/static_1014_01 --record-fps 30
```

程序只读取角度。`--frames 900` 表示最多处理 900 帧，**不承诺恰好 30 秒**；实际处理速度受推理和保存视频影响。按窗口中的 `q` 可以提前结束，或在终端按一次 Ctrl+C 请求正常收尾。若驱动没有返回图像，退出也可能等不到；这时按总计划排查，而不是再开一份程序。

输出四份同名前缀文件：

| 文件 | 内容 |
|---|---|
| `.avi` | 未画绿框的 BGR 图像，已完成驱动颜色转换和配置的图像旋转；不是 Bayer 传感器 RAW |
| `.csv` | 每帧的图像尺寸、时刻、候选数、四角、像素中心、最新串口回传 |
| `.config.yaml` | 本次启动使用的配置快照，不含模型权重副本 |
| `.session.txt` | 来源、阶段、播放帧率、保存帧数、正常收尾状态 |

正常结束会先关闭文件，再完整解码 AVI，核对帧数与 CSV 行数。出现 `complete_frame_count_verified` 表示采集结束时核对通过。强杀、断电或异常退出的文件仍保留，但不能假定录像完整。以后复制文件时也要保证没有漏传或截断。

AVI 固定按 `--record-fps` 播放，不等于相机实际 FPS。软件取帧时间在 CSV；一帧的 `capture_s` 与 `processed_s` 分别是驱动取出图像、YOLO 完成后检查数据的相对时刻。它们不是硬件曝光时间戳。

`feedback_received_s` 是电脑收到并解析最新回传的时间。回传协议没有采样时间戳，因此 `feedback_age_ms≈0` 不能证明相机和 IMU 严格同步，也不能证明总延迟为 0。

### 5.2 把 CSV 变成可读报告

```bash
python3 contest/analyze_field_session.py output/static_1014_01.csv
```

生成 `output/static_1014_01.report.md`。重点看：

- 是否连续只有一个合格蓝色候选；没有目标或多个候选集中在哪些帧。
- 图像处理年龄、回传年龄是否有明显峰值。
- 目标横坐标离画面中心多远；单帧突跳发生在哪。
- `.session.txt` 是否称正常收尾且帧数一致。

探针候选规则是：蓝色、分数至少 0.8、四角存在、中心位于画面内。`raw_detections` 已经是 YOLO 后处理返回的装甲板结果，并非神经网络未经筛选的全部框。多个候选时，CSV 中唯一目标和四角字段留空；终端仍可能为了预览打印其中一个，**以 CSV 的候选数判断是否唯一**。

“900 帧中 850 帧只有一个候选”是候选覆盖情况，不能称为 94.4% 检测准确率。没有人工真值时，无法知道那些框有没有框错。对旋转靶还必须区分正面可见与背面不可见。

### 5.3 再做手动慢扫或旋转录像

固定靶不动、手动慢扫云台，记录局部像素/角度关系：

```bash
./build/srm_live_pixel_probe --config configs/live_yolo_1011.yaml --port /dev/ttyACM0 --frames 600 --display --phase sweep --session output/sweep_1014_01
python3 contest/analyze_field_session.py output/sweep_1014_01.csv
```

固定云台、让靶旋转，只读记录：

```bash
./build/srm_live_pixel_probe --config configs/live_yolo_1011.yaml --port /dev/ttyACM0 --frames 1200 --display --phase rotating --session output/rotating_1014_01
python3 contest/analyze_field_session.py output/rotating_1014_01.csv
```

这些程序不可和无弹跟随程序同时运行：它们都会使用相机，串口也不应让多个程序竞争读取。每一轮完成后再开下一轮。

### 5.4 斜率算法在算什么

只在 `phase=sweep` 时拟合：`x = a × yaw + b`。斜率 `a` 的单位是像素/度。

```text
a = Σ[(yaw_i − 平均yaw) × (x_i − 平均x)] / Σ[(yaw_i − 平均yaw)²]
```

旧现场两端数据估计约 `+32.1 px/°`，含义是：在那次安装和局部视场中，回传 yaw 增大时，目标横坐标也增大。因此右侧目标需要负 yaw 修正。这里的正负关系来自实测，不能凭“右转应该是正号”猜。

新分析器要求至少 20 个有效成对样本、yaw 跨度至少 1°；筛掉过期图像、过期回传，以及取帧和回传接收时刻相差超过 100 ms 的样本。这个筛选仍不能建立硬件同步。扫描要慢，靶要固定；拟合后的 R² 高也不保证设备角度单位、时间或镜头参数完全正确。

**斜率是局部近似，不能代替相机内参。** 本工具不会把结果自动写进控制器。

### 5.5 导出中期能讲解的标注录像

```bash
python3 contest/render_field_session.py output/static_1014_01.csv --output-video output/static_1014_01_annotated.avi
```

它用原 AVI 和已记录的 CSV 画四角 0～3、目标中心、图像中心，以及回传新鲜性、角度和图像年龄。不会重新运行模型，因此画面和分析报告来自同一批检测结果。多个候选时不画唯一目标框。

输入 AVI 与 CSV 必须同名前缀且帧数、尺寸一致，否则停止输出。默认缩为 0.75 倍，沿用原 AVI 固定播放帧率；原文件保留，标注视频必须用新名称。`FRESH` 表示本地回传年龄不超过 250 ms，不表示硬件同步。

## 6. 录像标定：先把板拍对，再计算

先确认板的真实信息并记下来：

- 棋盘：每行、每列的**内角点**数；每个小格实测边长。10×7 个黑白格对应 9×6 个内角点。
- 圆点板：本工具支持黑圆白底的**对称**阵列；填写圆心列数、行数和相邻圆心间距。
- 镜头、对焦、相机分辨率、旋转和裁剪设置。标定后应保持这些几何条件一致。

`calibration/capture.cpp` 是旧开源 CAN 姿态采集入口，不适合直接套到本车 USB CDC 配置。本次改用纯相机录像，不依赖 CAN。

复制现场配置另存一份，调曝光使黑白格和角点清晰；固定相机，让板占据不同位置和大小，并分别左右、上下倾斜。在每个姿态短暂停住，避免录像里全是运动模糊。不能只拿同一个正对姿态晃几十秒。

```bash
cp -n configs/live_yolo_1011.yaml configs/calibration_field_1014.yaml
./build/camera_test --config-path=configs/calibration_field_1014.yaml --display --record-path=output/calibration_board_1014_01.avi --duration-sec=60 --record-fps=20
```

这段命令只复制配置，不会自动调亮画面；需在新文件中手动改 `exposure_ms` / `gain` 并复看板。不要在未确认清晰度时直接录完整一分钟。

**下面是待填写的命令模板，中文占位部分必须替换，不能原样执行：**

```text
python3 calibration/calibrate_from_video.py output/calibration_board_1014_01.avi \
  --board chessboard --cols 实际内角点列数 --rows 实际内角点行数 \
  --spacing-mm 实际小格毫米数 --stride 10 --max-views 40 --min-views 12 \
  --output-dir output/calibration_result_1014_01
```

圆点板把 `chessboard` 换成 `circles`，并使用圆心计数和间距。输出目录必须是新的；失败的那份目录保留用于排查，下一次另起名称。

### 算法和输出

1. 按间隔抽帧；找到完整棋盘角点或圆心。
2. 棋盘做亚像素定位，让坐标不只停留在整数像素；近似相同的图像布局被剔除。
3. 将规则格点赋予真实平面坐标，使用 OpenCV 的平面标定流程估计针孔相机矩阵 `K` 和 5 个畸变参数。
4. 用求得的参数把格点重新投影到图像，统计它们与检测点的差距。

```text
K = [ fx   0  cx ]      # fx/fy：以像素为单位的焦距
    [  0  fy  cy ]      # cx/cy：主点，不一定恰好在图像中心
    [  0   0   1 ]

distort_coeffs = [k1, k2, p1, p2, k3]
```

输出 `camera_intrinsics.yaml`、`views.csv`、`observations.csv`、`accepted/` 和 `report.md`。先检查角点预览，再看每幅误差、覆盖范围和参数。

重投影 RMS 是 `sqrt(所有点的像素距离平方之和 / 点数)`，它是参与求解图像的误差。小 RMS 不能单独证明 5 m 测距准确；应另录独立验证数据。板中心覆盖多个区域也不保证有足够倾角，程序无法替你确认板是否平整或格子是否量准。

此工具只标定相机内参和畸变，没有求相机到云台、枪口的外参。输出不会自动合并现场配置。

### 用独立棋盘录像核验距离

另录一段未参加标定的棋盘视频，保持镜头、对焦、分辨率、方向和裁剪状态不变。实测**相机光心到 8×11 内角点网格几何中心的直线距离**，不能把棋盘外框、镜头前沿或相机前向 `z` 深度当作同一个量。用实际量到的米数替换下面的 `实测距离`：

```text
python3 calibration/validate_board_distance.py output/新录棋盘视频.avi \
  --intrinsics output/标定结果/camera_intrinsics.yaml \
  --cols 8 --rows 11 --spacing-mm 30 --known-distance-m 实测距离 \
  --stride 15 --max-views 30 --min-views 5 \
  --output-dir output/新测距结果
```

输出新目录中的 `report.md` 和 `views.csv`：逐帧给出棋盘中心在相机坐标系中的 `x/y/z`、光心到中心的直线距离、相对实测值的偏差、重投影误差和有效内角点数。工具拒绝分辨率不匹配、角点不足，以及与内参源视频路径或字节内容相同的录像；它不会打开相机、串口或控制云台。若原标定视频不在本机，复制改名检查无法完成，报告会注明。真实距离接近与否仍须结合量距位置和视频清晰度判断。

## 7. 标定后：离线 PnP，先确认距离和角点定义

`evaluate_pnp_session.py` 读取新会话 CSV、已验证的内参文件、四个检测点对应的实际矩形宽高，输出相机坐标系下的几何解，**不控制云台**。以下同样是需替换中文数字占位的模板：

```text
python3 contest/evaluate_pnp_session.py output/static_1014_01.csv \
  --intrinsics output/calibration_result_1014_01/camera_intrinsics.yaml \
  --width-mm 四角矩形实测宽度毫米 --height-mm 四角矩形实测高度毫米 \
  --output-dir output/pnp_static_1014_01
```

输出 `poses.csv` 和 `report.md`。如果有实测的光心到目标中心距离，可加 `--known-distance-m 米数`，报告会对照欧氏距离误差；这段数据必须保持该距离真值不变。内参分辨率与会话不一致时程序会拒绝求解。

比赛规则的 140×125 mm 是靶面描述；当前 YOLO 的四角可能对应灯条端点。必须查看编号角点并量相应点之间的宽高，不能直接把靶面外轮廓尺寸填进灯条点模型。原 `solver.cpp` 中 135/230×56 mm 也是开源模型假设，不能当作本赛实测值。

PnP 的问题是：“已知矩形真实大小和镜头成像规律，四个像素点对应的矩形在相机前方哪里？”本工具用平面 IPPE 求解，并检查重投影误差和正深度。平面目标可能有两个相近解，数值上能求解不代表姿态唯一可信。

输出坐标采用 OpenCV 相机约定：x 向图像右、y 向图像下、z 向前。`z` 是前向深度；`sqrt(x²+y²+z²)` 才是从相机光心到目标中心的直线距离。它们不是云台 yaw/pitch，不能直接塞进串口角度字段。

尚需实物数据确认：内参、检测角点定义、实测尺寸、不同距离下的误差、相机到云台的坐标变换。通过这些环节后，才接后续运动估计与预测。

## 8. 离开现场要带走什么

- 每轮的 AVI、CSV、配置快照、会话状态和分析报告；单独录像的 AVI 与时间 CSV。
- 相机标定视频、板的尺寸照片、结果目录，以及一份未参与标定的验证视频。
- 无弹居中的终端日志、起始/最终偏差、是否真的进入中心、最终 mode 和回位角度。
- 镜头型号、焦距/对焦状态、相机安装方向、现场距离和靶的转动设置。
- 模型版本：保存配置使用的模型文件名称和 SHA-256，例如当前 YOLOv5 的 XML/BIN；不要只记“用了 YOLO”。

现场产生的原始录像是实验记录，不能把 `output/` 当成随时能删的缓存。复制到自己的电脑并核对数量和大小后，再整理旧文件。

## 9. 本轮软件验证与现场验证的区别

本机已验证：新探针编译、演示视频 30 帧录像与 CSV 对齐、正常退出收尾、覆盖/参数错误拦截；分析器异常数据与过期配对筛除；棋盘/圆板合成标定；11 项可重复运行的 Python 数据/几何自检，以及已有协议与无弹控制自检。

本轮还在本机修复了开源 Target 的二装甲越界、仿真构造状态未初始化及 Armor 优先级未初始化，并增加 C++ 回归检查。**这些跟踪器源码改动没有放进本次现场数据工具包**；包只更新数据工具及录像入口。后续接入完整开源链路时再审核部署，不能把本机修复说成 NUC 已验证。

这些结果说明工具具备进入现场验证的条件。它们不证明 NUC 已安装新版本，也不证明本车已完成标定、居中、旋转预测或比赛命中验证。每次汇报都用实际保存的证据更新结论。
